# rushwind-toolkit

[中文](./README.md) | **English** | [日本語](./README.ja-JP.md)

</div>

---

The RushWind ecosystem toolkit: the [`rush` CLI](#commands) plus the
[`rush-gen` core library](#repository-layout).

It covers the gaps that genuinely exist in the development chain of
[RushWind](https://github.com/tx7do/rushwind) (a Rust microservice
framework) and
[rushwind-admin](https://github.com/tx7do/rushwind-admin) (a
contract-driven admin scaffold).

Positioning: only what has no counterpart on the RushWind side — not an
everything-box. Contract and route generation is already covered by
rushwind-gen-http inside `build.rs` (protos in; route tables, error
mappings, and service traits out, zero hand-written routing), watching
and cross-compilation belong to the cargo ecosystem, and frontend page
generation is out of scope for this repository.

## Install

```shell
cargo install --git https://github.com/tx7do/rushwind-toolkit rush-cli
```

## Commands

| Command | Status | Description |
|---|---|---|
| `rush adopt` | ✅ | Turn a rushwind-admin snapshot from an upstream mirror into a downstream-owned repo |
| `rush manifest` | ✅ | Check / rebuild the sha256 manifests of the proto and react synced surfaces |
| `rush gen entity` | ✅ | Generate the full backend chain of a domain entity |
| `rush new` | ✅ | Scaffold a new project that compiles and runs with plain `cargo run` |
| `rush testbed` | ✅ | Differential-rig orchestration and report summaries (never starts docker) |

### `rush adopt` — downstream takeover (step one of secondary development)

Background: the proto contracts and the react frontend of rushwind-admin
are a mirror synced from go-wind-admin, protected by sha256 manifests
plus CI gates (semantics: "no hand edits"). That is right for the
maintainer and backwards for downstream adopters — adding your own
protos or editing your own frontend pages breaks CI, while the `sync`
mode that rebuilds the manifest requires the upstream checkout (at
`D:\GoProject\go-wind-admin` on Windows).

`rush adopt` switches the repo from mirror mode to owned mode:

1. Rebuilds `backend/api/MANIFEST.sha256` and
   `frontend/admin/react.MANIFEST.sha256` with the **current tree** as
   the baseline;
2. Strips the two sync gate steps (with their adjacent comment blocks)
   from `.github/workflows/ci.yml`;
3. Keeps the upstream-drift baseline `react.UPSTREAM.sha256` by default
   with a notice; `--prune-upstream-baseline` removes it.

Idempotent and re-runnable; `--dry-run` previews everything without
writing; `--keep-gates` rebuilds manifests only and leaves CI alone
(maintainer mode for those still tracking upstream).

```shell
rush adopt --dry-run   # preview
rush adopt             # take over
```

### `rush manifest` — manifest maintenance

After adopting, rebuild the baseline whenever you add or change protos
or frontend files so CI stays green:

```shell
rush manifest proto --rebuild   # backend/api/protos surface
rush manifest react --rebuild   # frontend/admin/react surface
rush manifest proto             # check only by default (read-only)
```

The manifest algorithms are byte-faithful ports of the shell scripts
they replace: the proto surface strips the UTF-8 BOM before hashing; the
react surface excludes `node_modules`/`dist` directories and git-ignored
paths (same semantics as `git check-ignore`), hashes byte-exact, and
requires execution inside a git work tree. Checks compare content maps,
so they are insensitive to row order and stay accurate against
pre-adopt manifests generated by the original scripts.

### `rush gen entity` — full backend chain of a domain entity

Generates the entire backend chain of a standard CRUD entity in
rushwind-admin (template baseline: the repo's smallest chain,
dict_type) — one command, a compiling skeleton:

```shell
rush gen entity widget \
  --field code:string --field quantity:u32 --field is_active:bool
```

What gets generated:

- Message-face proto: `backend/api/protos/widget/service/v1/widget.proto`
- Admin HTTP-annotated proto:
  `backend/api/protos/admin/service/v1/i_widget.proto`
  (List/Get/Create/Update/Delete routes, prefix defaults to
  `/admin/v1/widgets`)
- SeaORM entity: `backend/services/admin-api/src/data/sys_widgets.rs`
- Repo (`repo_shell!` macro + tenant-scoped batch delete):
  `backend/services/admin-api/src/data/repos/widget.rs`
- Service impl (matching the Handlers trait generated by
  rushwind-gen-http): `backend/services/admin-api/src/services/widget.rs`
- Five registrations (idempotent line-level insertion): `data.rs` /
  `migration.rs` / `data/repos/mod.rs` / `services.rs` /
  `server/rest.rs` (the use-import block + the mount table)
- The proto MANIFEST rebuilds automatically (`--skip-manifest` to skip)

Field types are `string|i32|u32|bool|f64`; the standard columns (id /
tenant_id / sort_order / auditor and timestamp triplets) ride along
automatically. `cargo check` goes green right after generation (verified
against the real rushwind-admin with a gizmo entity); follow up with
`cargo fmt`.

`--dry-run` previews every action without writing. Notes about deployed
databases and the manual follow-ups (seed / frontend / testbed) appear
in the command output.

### `rush new` — new project scaffold

```shell
rush new my-server && cd my-server && cargo run
```

The embedded template is self-contained: rushwind git dependencies
pinned at the same rev rushwind-admin consumes, one YAML document
assembling the memory storage engine, an automatic CRUD edge (`/items`),
and an HTTP server — after `cargo run`, `curl /health`, `/wired`, and
`/items` per the printed hints to see the whole chain. `git init` runs
by default (`--no-git` skips); `--dir` picks the parent directory.

`--template <dir>` accepts any external template (e.g. the rushwind
repo's `examples/bootstrap-demo`): the tree copies wholesale (skipping
`.git`/`target`), the template's Cargo.toml package name is inferred and
token-renamed (underscore variant included); non-text files pass
through byte-exact.

### `rush testbed` — differential-rig orchestration and report summaries

Collapses the three-step run book in `backend/testbed/README` into
commands. **Container discipline**: the Go reference side runs in the
docker differential stack, and rush never starts it — when the Go
endpoint is unreachable it fails immediately with the manual
instructions (`cd backend/testbed && docker compose up -d --build`).

```shell
rush testbed run     # build → start the Rust side (:7788) → replay via admin-diff → summarize
rush testbed report  # offline summary of a JSONL report (default backend/testbed/reports/report.jsonl)
```

What `run` orchestrates: preflight the corpus/exemptions/both crates →
probe the Go endpoint (stop if down) → if the Rust endpoint is down,
`cargo build` and start admin-api, wait for readiness → run the replayer
with the repo's default arguments (`--go/--rust/--corpus/--exemptions/--out`)
→ tear down the spawned process (`--keep-server` keeps it) → pass the
replayer's exit code through and summarize the report.

What `report` summarizes: the verdict histogram
(Ok/Fail/Exempt/Pending/Unreachable), the class×verdict matrix, the
beyond-exemption divergences (Fail) with their evidence, and the
unreachable case list — no more eyeballing raw JSONL.

## Repository layout

```
rushwind-toolkit/
├── crates/
│   ├── rush-cli/     # the `rush` executable entry (clap command surface)
│   └── rush-gen/     # core library: manifest pair + adopt + entity chain + project scaffold
└── ...
```

Core library and CLI are separated: a future desktop shell (if any,
leaning Tauri) reuses `rush-gen` directly without going through the CLI.
